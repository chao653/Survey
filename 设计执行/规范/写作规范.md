# 写作规范（Survey · UI 文案英文大小写）

> 本文约束 Survey 设计稿中**英文 UI 文案的大小写**（casing）。产出英文文案（按钮、标题、提示、空态等）或走查已有文案时按本文执行。
>
> 来源与改编：以 `~/Desktop/UX文字规范/UX文字大小写规范.md`（通用规范）为框架，叠加两层项目口径——① Asher 个人 House override（见 `ui-text-capitalization` skill）：**输出一律禁用 ALL CAPS**；② Kira 走查先例（Kira_Grading B-010/B-011）：控件类文案用 Sentence case。通用规范与本文冲突时，以本文为准。
>
> 范围：仅英文。中文文案、标点、全半角不归本文管。

## 一、核心原则

1. **一致性 > 规则本身**：同一画板内同一角色的文案必须用同一种风格。最常见的真实缺陷不是「选错风格」，而是混用（同页 `User Settings` 和 `Account settings` 并存）。
2. **可读性优先**：超过三四个词的文本一律 Sentence case。
3. **强调要克制**：Title Case 用得越少越有力，不要什么都 Title Case——这是产文案时最常见的错误。
4. **禁用 ALL CAPS**（House override）：任何场景不输出全大写，包括通用规范允许的按钮 / Tag / Badge / 紧凑导航。走查中遇到已有的 ALL CAPS 时单独标记、交用户定夺，不擅自改小写。
5. **禁用 all lowercase**：Kira 不是极简品牌风格产品，全小写不进入选项。

## 二、可用风格（两种）

| 风格 | 规则 | 示例 |
| --- | --- | --- |
| **Sentence case（默认）** | 仅首词首字母大写，其余小写（专有名词除外） | `Upload one or more student submissions to grade them.` |
| **Title Case（层级标题）** | 主要词类（名/动/形/副/代词）首字母大写；冠词、并列连词、短介词小写；首末词一律大写 | `Add Student Submissions` / `Back to the Top` |

拿不准时用 Sentence case。

## 三、组件映射表（Kira 版）

| 组件 | 用哪种 | 备注 |
| --- | --- | --- |
| 按钮 / CTA | Sentence case；≤3 词可 Title Case | 禁 ALL CAPS、禁全小写。staging 现例：`Upload` / `Import` / `Paste` / `Next` |
| 表单字段 Label | Sentence case | 输入框上方说明 |
| Placeholder | Sentence case | 引导提示，不用 Title Case |
| 页面 / 步骤标题 | Title Case | staging 现例：`Add Student Submissions` |
| 分区标题（Section heading） | Title Case | staging 现例：`Files Source` |
| 卡片标题 | Title Case | 强化层级 |
| 导航 / 菜单 | Title Case | 多为功能名（`Grading Studio`），本身按专有名词处理 |
| 筛选 chip / 状态文案 | Sentence case | Kira 先例（B-010）：`Needs grading` / `Graded & unreleased`；不学设计稿旧版的 Title Case |
| 展开收起 / 行内小控件 | Sentence case | Kira 先例（B-011）：`+9 more` / `Show less`，两处风格要一致 |
| Tag / Badge / 状态 pill | Title Case | `New` / `Beta` / `Pending`，不写 `NEW` |
| 辅助文本 / Helper text | Sentence case | 长文本一律如此 |
| 错误提示 | Sentence case | 自然语言 |
| Tooltip | Sentence case | 短句 |
| Modal / Dialog 标题 | Sentence case | 陈述式、提问式均可 |
| 空态文案 | Sentence case | 参考现例：`Nothing here right now.` |

## 四、决策树

```
是 Survey 的功能名、产品名？（见第五节）
  └─ 是 → 保留固定写法，不套任何规则
  └─ 否 ↓
是容器/层级标题？（页面、分区、卡片、导航）
  └─ 是 → Title Case
  └─ 否 ↓
其余一切（按钮、chip、提示、正文、错误、空态…）
  └─ Sentence case ✅（默认）
```

## 五、专有名词清单（不受大小写规则影响）

产品/功能名按固定写法原样使用，Title Case / Sentence case 环境中都不改动。以下为 Survey 项目清单，随 PRD 与设计推进逐条登记（来源写明 PRD 锚点或用户确认）：

- 产品名：`Survey`（Linear 项目描述用法；项目名 `Survey 1.0` 只用于工单，不进 UI）
- 关联产品名：`Kira AI`、`Student Atlas`（Linear 项目描述固定写法）
- 功能 / 模块名（Linear 项目描述写法，待对照 PRD 核准）：`AI Summary`、`Instructor Response`、`Results`（页面名）
- 待填：题型名（见 `需求文档/00_PRD溯源.md` 的题型契约文档）、starter / 模板等入口名的固定写法
- 状态名：待填（PRD 固定写法，注意多词状态名第二词是否小写）
- 通用缩写：`AI`、`PDF`、`CSV`、`URL`（按需增补）
- 混合场景：专有名词保留自身写法，其余词照常套规则（如 Sentence case：`Import from Google Drive`）

## 六、常见错误对照

| ❌ 错误 | ✅ 正确 | 原因 |
| --- | --- | --- |
| `Please Enter Your Email Address`（placeholder） | `Please enter your email address` | 提示类是正文角色，Sentence case |
| `SUBMIT`（按钮） | `Submit` | House override：禁 ALL CAPS |
| `submit form`（按钮） | `Submit form` | 按钮不用全小写 |
| `Needs Grading`（筛选 chip） | `Needs grading` | Kira 先例 B-010：控件文案 Sentence case |
| 同页 `+9 More` 与 `Show less` 混用 | `+9 more` / `Show less` | 同角色风格必须一致（B-011） |
| `ARE YOU SURE YOU WANT TO DELETE THIS?` | `Are you sure you want to delete this?` | 长文本禁全大写 |

## 七、与工具的配合

- **产文案（authoring）**：写英文文案时直接按本文出稿，不必向用户解释选了什么风格；非显然的选择一句话带过即可。
- **走查（audit）**：审已有设计稿的大小写时，用 `ui-text-capitalization` skill 的 Mode B 从 Figma 拉全部文本层逐条核对；发现 ALL CAPS 按 House override 单独列出交用户定夺。
- 本文与该 skill 口径一致；若日后 House override 调整，两处同步改。
